## Versión en español

**Six ways an LLM can edit your code**

Hace unos meses me propuse hacer un mini editor online para crear sketches de p5.js: visuales y pequeños widgets con IA asistida. Empezó como otro de mis proyectos cortos y terminó siendo un monstruo en el que sigo trabajando hasta hoy.

La idea original era recibir pequeños hints de código. En el camino aparecieron integraciones con varios proveedores de LLMs (OpenAI, Anthropic, Groq, DeepSeek), streaming de respuestas por SSE, prompt caching para bajar costos, límites de tokens y de rate, inputs con imágenes, revisión de cambios con diffs... y el gran desafío: cómo hace el modelo para editar el código. Un LLM solo puede emitir texto, así que necesitás un contrato: el modelo expresa el cambio en un formato y vos lo parseás y lo aplicás. Ese formato define tu factura de tokens, tu latencia y cuántas ediciones fallan.

Las seis formas que existen hoy:

1. Full-file rewrite: el modelo reescribe el archivo entero. Nunca aplica mal, pero pagás cada línea que no cambió.
2. Line-number edits: "reemplazá la línea 7". Mínimos tokens, pero los modelos no saben contar líneas.
3. Unified diff: el formato de git. Funciona solo si el applier ignora los números de línea del hunk y busca las líneas de contexto.
4. Search/replace blocks: citar el código a cambiar y su reemplazo. El sweet spot: ~30 tokens en vez de ~2.400 para el mismo cambio.
5. Lazy edit + apply model: el modelo grande esboza el cambio y un segundo modelo fine-tuneado lo mergea a ~1.000 tokens/s. Lo que hace Cursor.
6. Structural (AST) edits: direccionar por función en vez de por posición. Preciso, pero de granularidad gruesa.

El patrón de fondo: la confiabilidad depende de qué le pedís al modelo que cite. Los formatos que citan posiciones fallan, porque los transformers no cuentan bien. Los que citan contenido funcionan, porque reproducir texto que acaba de leer es su habilidad central.

Armar esto a mano me hizo dimensionar lo que resuelven productos como Cursor o Aider cuando implementan edición de código a escala: el formato es solo el principio, después viene todo el trabajo del lado del cliente cuando el modelo no coopera. Y de paso es de los mejores ejercicios que encontré para formarme como AI Engineer: prompting, formatos de salida, economía de tokens, caching y evaluación de fallas, todo en un proyecto propio.

En las imágenes va el detalle de cada formato, con sus pros y contras.

## English version

**Six ways an LLM can edit your code**

A few months ago I set out to build a small online editor for p5.js sketches: visuals and little widgets, with AI assistance. It started as another one of my short side projects and turned into a monster I am still working on today.

The original idea was getting small code hints. Along the way came integrations with several LLM providers (OpenAI, Anthropic, Groq, DeepSeek), SSE response streaming, prompt caching to keep costs down, token and rate limits, image inputs, diff-based change review... and the real challenge: how does the model actually edit the code. An LLM can only emit text, so you need a contract: the model expresses the change in some format, and you parse it and apply it. That format determines your token bill, your latency, and how often edits fail to land.

The six formats in use today:

1. Full-file rewrite: the model resends the whole file. Never lands in the wrong place, but you pay for every unchanged line.
2. Line-number edits: "replace line 7". Minimal tokens, but models cannot reliably count lines.
3. Unified diff: git's format. Only works when the applier ignores the hunk line numbers and searches for the context lines instead.
4. Search/replace blocks: quote the code to change, then its replacement. The sweet spot: ~30 tokens instead of ~2,400 for the same edit.
5. Lazy edit + apply model: the big model sketches the change and a second fine-tuned model merges it at ~1,000 tokens/s. What Cursor does.
6. Structural (AST) edits: address by function instead of position. Precise, but coarse-grained.

The underlying pattern: reliability tracks what the model is asked to quote. Formats that quote positions fail, because transformers cannot count. Formats that quote content work, because reproducing text it just read is the core skill.

Building this by hand made me appreciate the scale of what products like Cursor or Aider take on when they implement code editing: the format is only the start, then comes all the client-side work for when the model does not cooperate. It has also been one of the best exercises I have found for growing as an AI Engineer: prompting, output formats, token economics, caching, and failure analysis, all inside one project.

The images break down each format with its pros and cons.
