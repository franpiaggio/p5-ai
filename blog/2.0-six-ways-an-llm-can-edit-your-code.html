Six ways an LLM can edit your code

A taxonomy of edit formats, from the dumbest to the most industrial. The same one-line change expressed in every format, with each format's characteristic way of failing.

Section 1The contract problem

A language model cannot reach into your editor and move the cursor. It can only emit text. So every AI coding tool needs a contract with its model: when you want to change the code, express the change in this format, and I will parse it and apply it. The format you choose determines your token bill, your latency, and, above all, how often edits fail to land.

This piece walks through the six formats in use today, simplest first. While building an AI editor for p5.js sketches I ended up trying or studying all of them, and the interesting part is that each one fails in its own characteristic way. The failures, more than the successes, explain why the industry settled where it did.

One running example throughout. The file is a 17-line p5.js sketch, and the user asked for a warmer background. The change is one line:

// line 7, inside draw():
-  background(30);
+  background(48, 24, 38);

Here is what that one-line change looks like in each format.

Section 2 · Format 1Full-file rewrite

The model sends the entire file again, changed line included:

function setup() {
  createCanvas(windowWidth, windowHeight);
  rectMode(CENTER);
}

function draw() {
  background(48, 24, 38);
  translate(width / 2, height / 2);
  // ...ten more lines, all identical to what you already have
}

This is what raw ChatGPT does, and it is worth taking seriously before dismissing it: it is the most reliable format that exists. There is nothing to match, nothing to locate, no way to apply the edit in the wrong place. Parsing is trivial. For brand-new files it is the only option, and for small files it is honestly fine.

The failure is economic, and it scales with file size. You pay output tokens (the expensive kind) for every unchanged line, and you wait for them too, because generation is sequential. A one-line change to a 300-line file costs roughly 2,400 output tokens and arrives at typing speed. There is also a subtler failure: models get lazy on long rewrites and truncate or elide ("rest of the file unchanged"), which silently deletes everything they didn't repeat. A format whose worst case is deleting most of the file needs guardrails.

Verdict. Perfect reliability, worst economics. Right for new files and genuine rewrites; wasteful for everything else.

Section 3 · Format 2Line-number edits

The obvious optimization: address the change by position instead of repeating content.

{ "start_line": 7, "end_line": 7,
  "replacement": "  background(48, 24, 38);" }

Minimal tokens, trivially parseable, and it looks like an API call, which makes it attractive for tool-calling designs. It is also the format that fails most often in practice, for a reason that sounds like a joke but is thoroughly documented: language models cannot reliably count lines. A model reads the file as a token stream, not as a numbered grid; its idea of "line 7" comes from soft attention, not from an index. It is frequently off by one or two, and off-by-one in this format means the edit lands on the wrong line with complete confidence.

There is a second failure baked in: staleness. If the model emits three edits in one reply, applying the first one shifts every line number below it. Either the model has to predict the shifted positions of its own future edits (it can't), or the client has to apply edits bottom-up and hope no ranges overlap. Every tool that has tried pure line-number addressing has either abandoned it or wrapped it in verification.

Verdict. Best economics on paper, worst reliability in practice. Positions are the one thing models are bad at quoting.

Section 4 · Format 3Unified diff

The format git has used for decades, and the one every model has seen millions of times in training:

@@ -4,7 +4,7 @@
 function draw() {
-  background(30);
+  background(48, 24, 38);
   translate(width / 2, height / 2);

Compact, familiar, and it carries context lines, which is a real improvement over bare positions: the context anchors the change to content, not just to a number. GPT-4 Turbo in particular got measurably less lazy when asked for diffs instead of full files; Aider's benchmark run on lazy-coding tasks cut task failures roughly in half by switching to diffs.[2]

But the hunk header is a line-number edit hiding inside a better format. @@ -4,7 +4,7 @@ claims "starting at line 4, seven lines". Models get those numbers wrong constantly, and a hunk whose numbers don't match its context is, by the strict rules of patch, unappliable. Aider's fix is telling: their applier ignores the line numbers entirely and locates hunks by searching for the context lines instead.[2] Which means the thing that makes LLM unified diffs work is quietly turning them into the next format on this list.

Verdict. Good economics, mediocre reliability as specified. Only works when the applier stops trusting the part of the format that makes it a diff.

Section 5 · Format 4Search/replace blocks

Drop the pretense of positions altogether. Quote the code to change, then the code to change it to:

<<<SEARCH
  background(30);
===
  background(48, 24, 38);
>>>REPLACE

This works because it asks the model for the one thing it is genuinely good at: quoting text it just read. No counting, no arithmetic, no bookkeeping across edits. Aider's public benchmarks across models settled on this as the most reliable practical format,[1] and it is what my editor uses: the one-line change above costs about 30 output tokens instead of 2,400.

Its characteristic failure is subtler than the others: near match. The model reconstructs the SEARCH text from attention over a long context and drifts on invisible details: a trailing space, tab width, a semicolon. A naive indexOf applier then reports "not found" for an edit that is 99% correct. The mitigations are client-side and well understood: cascading match tolerance (exact, then whitespace-insensitive, then indentation-insensitive), and a hard rule that fuzzy matches must be unique in the file, because applying an edit in the wrong one of two candidate locations is far worse than failing. I covered the full cascade in article 1, section 5.

Verdict. The practical sweet spot: good economics, high reliability, and its failures are fixable on the client. This is the format to beat.

Section 6 · Format 5Lazy edit + apply model

The industrial answer, used by Cursor. Let the big model write the change the way models naturally want to, sketchy and incomplete:

function draw() {
  background(48, 24, 38);
  // ... existing code ...
}

Then hand that sketch, plus the real file, to a second model: a small one, fine-tuned exclusively for merging, running under speculative decoding at around a thousand tokens per second.[3] The big model spends its intelligence deciding what to change; the apply model spends its speed working out where. Laziness stops being a failure mode and becomes the format itself.

The catch is the price of admission: you have to train, host, and serve a custom model, and its mistakes are a new failure surface that you own. This is the right trade for a company whose product applies millions of edits a day. For everyone else, a heuristic approximation covers a surprising amount of the ground: detect that a block is a fragment (it starts mid-scope, or is far too short to be the whole file), then anchor its unique lines against the file and replace the spanned region. That client-side version is article 1, section 6.

Verdict. The best user experience in the business, bought with a second model. Approximable client-side if you accept refusing the unmergeable cases.

Section 7 · Format 6Structural edits

The formats so far treat code as text. The last family treats it as structure: address the edit to a syntactic unit instead of a location.

{ "replace_function": "draw",
  "body": "function draw() {\n  background(48, 24, 38);\n  ..." }

The appeal is real: function names are stable addresses. They survive the file being edited above them, they can't be off by one, and a parser can verify the result compiles. Tools in the refactoring tradition, and some agent frameworks, use exactly this.

Why hasn't it won? Three quiet costs. The unit of edit is the whole function, so a one-line change inside a 60-line draw() resends 60 lines: the economics regress toward the full rewrite. Not every edit lives inside a neat unit: imports, top-level constants, comments, and CSS have no function name to address. And the applier now needs a parser per language, which turns a text-pipeline problem into a compiler-tooling problem. Structural editing shines for mechanical refactors done by deterministic tools; as an LLM output format, the text-based formats beat it on flexibility and cost.

Verdict. Precise addressing, coarse granularity. Great for tooling-driven refactors, rarely optimal as a model's output format.

Section 8Choosing

Laid side by side:

FormatAddresses byReliabilityCost for a 1-line edit
Full rewritenothingHighestWhole file
Line numberspositionLowestMinimal
Unified diffposition + contextLow as specifiedLow
Search/replacecontentHighLow
Lazy + apply modelcontent, learnedHighLow + a second model
Structuralsyntax treeHigh per unitWhole unit

The pattern behind the table: reliability tracks what the model is asked to quote. Formats that make it quote positions fail, because counting is not something transformers do well. Formats that make it quote content succeed, because reproducing text it just read is the core skill. Every format the industry actually ships lands on content-addressing, either explicitly (search/replace), by retrofit (Aider's diffs with ignored line numbers), or by learning it (Cursor's apply model).

For my p5.js editor the answer was the model-free branch: search/replace with a client-side matching cascade, full rewrites for new sketches, and a fragment guard for the day a small model gets lazy anyway. How those three pieces fit together, and what broke before they did, is article 1.
